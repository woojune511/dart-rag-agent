# 소제목 범위 수정과 검증

2026-09-29. [원인 진단](heading_scope_diagnosis.md)의 후속 수정.
제품 파서 수정과 provider-free 검증이며, LLM 정답률 비교나 저장소 재구축은 아니다.

## 수정 계약

- `financial_parser.py`의 plain 문단 처리도 번호형 독립 제목, 명시적인 굵은
  `SPAN` 제목, 문단 시작의 인라인 대괄호 제목을 인식한다. 일반 본문 속
  대괄호·연도형 문장·문장 종료 표현을 무조건 제목으로 승격하지 않는다.
- 새로 인식한 제목도 원문 본문에 보존한다. 제목 이벤트와 실제 XML 문자 위치를
  별도로 연결하므로 숫자·단위·문장을 제목 처리 때문에 삭제하지 않는다.
  기존 단독 대괄호 제목과 표 캡션의 처리는 유지한다.
- 대괄호 제목 앞에서 관측한 번호형 상위 항목을 스택에 보존한다. 그 상위 수준으로
  돌아오는 제목이 나오면 하위 대괄호 범위를 종료한다. 관측된 상위 항목이 없으면
  번호만 보고 임의로 대괄호 범위를 종료하지 않는다.
- 정상적인 하위 번호 항목, 대괄호 동급 항목, 표 캡션은 구분한다. 제목 경로를
  축약할 때 중간의 대괄호 주체가 빠지지 않게 한다.
- 회사명·질문·신용평가 등 주제별 분기는 추가하지 않았다. 검색·답변 모델과
  프롬프트·출처 검사 API는 변경하지 않았다.

변경 owner: `src/processing/financial_parser.py`. 기존 block collection과 chunker는
새로 인식된 제목·scope를 받아 기존 경계 분리 계약을 실행한다.

## 실제 보고서 비교

기존과 동일한 11개 원본의 `1. 회사의 개요` 절을, 수정 전 HEAD의 파서와 수정한
파서로 각각 재처리했다. 네트워크를 차단했으며 실험용 regex adapter는 사용하지 않았다.
전체 문서 ingest 대신 같은 절에 대한 수집·청킹과 구조화 표 자료를 비교했다.

| 확인 항목 | 결과 |
| --- | --- |
| KB금융 등급 표의 소제목 | 이전 자회사 제거, `아. 신용평가` 범위로 연결 |
| KB금융의 이전 자회사 설명과 등급 표 | 같은 청크에 합쳐지지 않음 |
| 삼성전자 신용평가 설명 | `[DX 부문]` 제거, `사. 신용평가` 범위로 연결 |
| 삼성전자 인라인 주체 | DS·SDC·Harman 제목을 각각 인식 |
| 11개 절의 전체 본문 | 공백 정규화 후 문자 순서와 내용 동일 |
| 112개 표 | 원문 표 텍스트·ID·헤더 보존 |
| 구조화된 33개 행·135개 값 | 실제 `*_records_json` 직렬화 내용 동일 |
| 표의 단위·기간·statement/scope metadata | 수정 전후 동일 |
| TableObject | 의도적으로 바뀐 `source_contexts` 외 모든 필드 동일 |
| 수정 후 문맥 출처 | XML XPath와 문자 구간으로 원문 정확 일치 |
| 원본·기존 corpus·직전 실험·이전 진단 | 804개 보호 파일 hash 동일 |

구조화 행·값 개수는 parser가 별도 record로 만든 부분의 수다. 모든 숫자가
이 records에 들어간다는 뜻은 아니며, 나머지도 전체 표 텍스트 비교로 보존을 확인했다.
첫 replay는 표 텍스트·ID·헤더를 검사했고, 추가 검증에서 실제 직렬화 record 필드와
TableObject까지 대조했다.

절 내 청크 수는 **121 → 175**다. 새 항목 경계가 인식돼 분리가 늘었으며,
입력 전체 크기·검색 순위·답변 비용의 동일성을 주장하지 않는다.
검토한 11개 절은 기존 보고서이며 독립 holdout이나 전체 문서 범위 검증은 아니다.

## 회귀 테스트와 저장소 호환성

`tests/test_plain_heading_scope.py`의 10개 테스트는 관측된 상위 번호 복귀,
정상 하위 항목, 상위 번호가 없는 대괄호 범위, 인라인·한 문단의 복수 제목,
원문 문자 구간, caption, 비제목 본문, structured 모드 및 구버전 store 거절을 다룬다.
수정 전에는 최초 6개 중 4개가 실패했고 수정 후 통과했다.

파서 schema는 `financial_parser_v3_heading_scope`로 올렸다. 기존 v2 store를
현재 파서 산출물로 묵인하지 않고 readiness mismatch로 구분한다. 기존 파일을
자동 변경하지 않는 테스트도 통과했다. 실제 기존 store는 아직 재구축하지 않았다.
따라서 새 파서가 설치됐다는 사실이 기존 저장 청크나 검색 결과까지 수정됐다는 뜻은 아니다.

전체 테스트의 첫 실행은 2,139개 중 기존 current-status 문서 길이 제한 한 건만 실패했다.
과거 checkpoint를 별도 이력 문서로 그대로 옮기고 현재 문서에서 연결했다.
최종 전체 검증은 **2,139/2,139 통과 (54.273초)**다.
실행 명령: `.venv/Scripts/python.exe -X utf8 -m unittest discover -s tests`.
`git diff --check`도 통과했다. 테스트 로그는 원래 실패 로그와 최종 통과 로그를
각각 보존했다. 계약을 약화하거나 테스트를 제외하지 않았다.

## 산출물과 제한

`verify_reports.py`, 보고서별 전후 블록·새 청크, `verify_table_payloads.py`,
보호 hash, 구조화 표 비교, 테스트 로그를 별도로 저장했다. 기존 결과는 덮어쓰지 않았다.
API/임베딩 호출 0, API 비용 USD0, store 쓰기 0. 모델 답변 개선 여부는 **NOT_RUN**이다.

원문에 경계 신호가 부족하거나 제목을 본문과 유일하게 나눌 수 없는 모든 경우를
해결했다고 주장하지 않는다. 특히 새 파서를 사용한 전체 store 후속 생성과
검색·답변 효과 평가는 별도 범위다.
