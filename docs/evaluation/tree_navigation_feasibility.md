# 문서 계층 탐색 가능성 점검

2026-09-30. **COMPLETE_OFFLINE_TREE_FEASIBILITY; NOT_READY_FOR_TITLES_ONLY_LLM_TREE_SEARCH**.

11개 보고서의 저장 청크15,608개를 모두 제목·절·원문 참조에 연결했다. 그러나 물리적
XML 중첩과 기존 parser의 정규화 목차가 어긋나는 구간, 그리고 하위 제목 없이 수백 개
청크를 가진 절이 있다. 따라서 이 구조를 그대로 유료 LLM 목차 탐색에 투입하지 않는다.
이번 산출물은 **PageIndex 아이디어를 검토하는 로컬 구조 진단**이다. PageIndex 패키지를
설치·실행하거나 공식 구현의 품질을 평가한 결과가 아니다.

## 범위와 고정 규칙

- 기존11개 2023 보고서 원본, v5 저장소의 JSON graph/payload, 기존 parser의 XML 복원과 section path 함수를 재사용했다.
- 원본을 다운로드하거나 재임베딩하지 않았다. JSON sidecar와 원본 파일만 읽고 Chroma/SQLite 클라이언트는 열지 않았다.
- XML SECTION/TITLE의 물리적 부모 관계와 저장된 intermediate_heading 순서로 별도 탐색 구조를 만들었다. 제목 문자열만으로 서로 다른 위치를 합치지 않는다.
- 노드에는 XML 위치·출처 hash·제목 원문을, 청크에는 기존 ID·텍스트/metadata/payload hash·부모 참조를 보존한다. 텍스트는 기존 graph에서 그대로 조회한다.
- 질문·골드는 구조 생성의 입력이 아니다. 고정 대표근거27개의 주소 연결은 구조를 만든 뒤에만 확인했다.
- non-SECTION ancestor title은 원문 문맥으로 보존하지만 탐색 노드로 사용하지 않는다. 예를 들어 문서 BODY의 목차 제목은 모든 절의 의미적 부모로 취급하지 않는다.
- 없는 제목을 LLM으로 생성하거나, 질문에 맞춰 절을 재배치하거나, 기존 parser·metadata를 수정하지 않았다.
- 한 번에 표시할 자식 메뉴를 65,536바이트로 점검한다. 이는 진단용 한도이며 provider context/token/cost 검증이나 정식 호출 계약이 아니다. 초과 메뉴를 자르지 않고 거절한다.

## 문제1: 물리적 XML 트리를 그대로 목차로 쓸 수 없음

POSCO홀딩스의 **52개 절 노드**에서 복원 XML의 부모 경로와 기존 parser의 정규화된
section_path가 다르다. 그 경로 아래 저장 청크는 중복 제거 후 **1,775개**다.
나머지10개 보고서에서는 이 비교 기준의 불일치가 없었다.

예를 들어 동일 원문의 위치가 물리적으로는 아래처럼 중첩된다.

`I. 회사의 개요 → 2. 회사의 연혁 → 3. 자본금 변동사항`

기존 parser의 section_path는 `I. 회사의 개요 → 3. 자본금 변동사항`이다.
고정 대표근거 POS_T1_057의 경로에도 회사 연혁 아래 경영진단 대목차가 붙는 차이가 있다.

이는 **새로 만든 물리적 트리를 그대로 채택할 수 없다는 진단**이다. 현재 제품이
그 경로로 LLM 탐색을 수행하고 있다는 뜻이나, 이전에 고친 소제목 버그가 재발했다는
판정은 아니다. 원본 XML 자체와 recover 파싱 각각의 기여를 분리하지 않았으므로
원인을 한쪽으로 단정하지 않는다. 기존 `_sanitize_path_titles`는 같은/상위 수준
제목을 만날 때 이전 path 항목을 정리하지만, 실험용 물리적 트리는 이를 부모 edge에
적용하지 않았다. 두 표현을 섞지 않고 불일치를 별도 보존했다.

후속 트리는 원문 제목의 위치를 보존하면서 기존 정규화 목차와 일관된 부모를
유일하게 연결하는 계약이 먼저 필요하다. 동일 표제·누락 부모·불명확한 대응을
검사하고, 유일하게 복원되지 않으면 보류해야 한다. 이번에 edge를 보정하지 않았다.

기존 입력 한도를 유지할 수 없다. 개별 저장 청크 본문은 모두 이 byte 한도 이하이나,
질문·metadata·출처를 포함한 최종 답변 packet의 적합성은 별도로 검사해야 한다.

따라서 후속 후보는 **정규화 목차에서 절 선택 → 선택된 절 안에서 기존 hybrid 검색 →
최종 원문8개**다. 상위 구조가 검색 범위를 줄이는지부터 비교할 수 있다. 순수 제목
탐색을 원한다면 먼저 주석 내 원문 표제·표 위치를 더 세밀하게 노출하는 별도 작업이
필요하다. 어느 방향도 이번에 구현·실행하지 않았다.
