# 값 없는 표제 청크의 생성·검색 경로 진단

2026-10-15 · `COMPLETE_SOURCE_AND_RANKING_DIAGNOSIS` · provider-free

**C10에서는 원본부터 분리된 표제·값 표를 각각 검색 문서로 색인하는 방식, Dense의 관련성 순위, RRF의 두 채널 중복 가산이 함께 작용했다.** 요청한 값이 파싱 과정에서 사라지거나, 긴 표를 자르다가 표제만 떨어진 사례는 아니다. 저장된 Dense와 RRF 계산에서 구현 오류는 재현되지 않았다.

이 진단은 [키워드 접두어 제거 비교](keyword_prefix_bm25_ablation.md)에서 확인한 C10 회귀를 추적한다. 코드·청킹·검색 조건은 바꾸지 않았으며 답변 생성, 재임베딩, 앱 store 변경도 없다.

## 원본에서 검색 입력까지

코웨이 접수번호 `20260323000924`의 다음 두 표를 원본 XML byte 범위와 현재 파서의 XPath로 연결했다. 이하 출처 표기는 chunk UID 끝부분이다.

| 단계 | 표제 `400:295` | 바로 다음 값 표 `401:296` |
| --- | --- | --- |
| 원본 위치 | `TABLE-GROUP[36]/TABLE[3]` | 같은 그룹의 `TABLE[4]` |
| 그룹 | `{XBRL}NT_C_D851100`, 연결 현금흐름표 주석 | 동일 |
| 원본 byte 범위 | 2,611,214–2,611,856 | 2,611,858–2,636,960 |
| 원본 내용 | 영업활동현금흐름 / 당기 / 단위 천원 | 퇴직급여·감가상각비 등 조정 및 자산·부채 변동의 상세값 |
| 구조 | 2행·2열, 값 레코드0 | 39행·2열, 값 레코드38 |
| 파싱 결과 | 독립 table block | 독립 table block |
| 청킹 결과 | 34자, `table_view=full`, 청크1개 | 940자, `table_view=full`, 청크1개 |

원본의 두 `TABLE` 사이에는 줄바꿈2bytes만 있다. 별도 주석 `748:261`→`749:262`, 주당이익 표제·값 표2쌍도 같은 물리적 분리를 확인했다. **네 쌍 모두 한 원본 표를 청커가 쪼갠 것이 아니다.**

현재 파서는 작은 표라도 허용된 날짜·단위·재무제표 제목 문법을 완전히 만족할 때만 다음 표의 context로 소비한다. `영업활동현금흐름`, `주당이익`처럼 그 문법 밖의 표제는 원문 보존을 위해 독립 table block으로 남는다. 이 사례는 2행·2열 크기 조건은 통과하고 **라벨 문법 검사에서 거절**된다. 끝의 명시적 단위만 다음 표로 전달된다. 관련 owner는 `financial_parser.py:99,324,361,382`, `block_collection.py:115`다.

청커는 이미 대기 중인 표가 있는데 다음 표를 만나면 먼저 청크를 확정한다(`chunking.py:385`). 따라서 합쳐도2,500자보다 작은 표제와 값 표가 별개 청크가 된다. 일반 용어로 만든 재현 fixture에서도 `chunk_size=2500`과`10000` 모두2청크였다. 반대로 처음부터 한 XML TABLE에 제목과 값이 있으면 이 fixture는1청크다. 크기 조정만으로 이 경계를 해결할 수 없다.

## 값과 연결 문맥은 어디에 남는가

**C10이 요구하는 본표는 `104:5`다.** 앞의 표제 바로 뒤 `401:296`과는 다른 표다. 원본 연결 현금흐름표 `{XBRL}CF_C`의 36행·4열·값 레코드105개가 2,134자짜리 청크1개로 보존된다. 필요한 영업활동 현금흐름35,544,145,039원과 당기순이익617,510,076,654원이 모두 원본·파서 블록·청크·색인 텍스트에 있다.

`401:296`은 조정·자산부채 변동 상세표이므로 표제에 이 표를 붙인다고 C10의 두 피연산자가 확보되지는 않는다. 주당이익의 인접 값 표 `396:291`에 있는617,724,967,901원도 지배기업 소유주 몫으로, C10이 요청한 전체 당기순이익과 다르다. 물리적 인접성과 질문에 필요한 근거는 별도로 판단해야 한다.

문맥은 완전히 삭제된 것이 아니라 **표현 계층에 따라 다르게 보존**된다.

- `401:296`의 `table_object_json.source_contexts`에는 원본 표제와 `당기`, 상위 `36. 현금흐름표 (연결)` 제목이 출처 위치와 함께 남는다.
- 반면 평면 metadata의 `period_labels`는 비어 있고 `period_focus=unknown`이다. 전달된 `unit_hint=천원`은 남는다. 전기 값 표 `402:297` 앞의 단순 `전기 / 단위` 표는 허용 문법에 맞아 전기 라벨이 전달된다.
- 현재 색인용 접두어는 이 전체 `source_contexts`를 읽지 않는다. `401:296`의 검색 텍스트에는 앞 표제 `영업활동현금흐름`이 없으며, 기본 `SimpleRagAgent`의 제한된 context 필드에도 전체 구조 객체가 포함되지 않는다. 구조화 저장의 보존과 실제 검색·답변 입력의 보존이 동일하지 않다.
- 기존 opt-in caption attachment는 명시적 날짜·단위만으로 구성된 캡션을 대상으로 한다. 이번 제목 포함 표제4개는 그 검출 조건에도 맞지 않는다. 기본 앱에서는 이 기능 자체가 꺼져 있다.

이는 `source_context.py:109`, `financial_parser.py:929`, `benchmark_runner.py:1687`, `src/config/simple_rag.py`의 현재 경계에서 확인했다. 표제 문법에 발견한 단어를 추가하거나 숫자 없는 청크를 일괄 삭제하지 않았다. 원문 설명·단위·기간을 잃지 않는 검색 표현이 검토 대상이다.

## BM25·Dense·RRF에서 실제로 일어난 일

아래는 원래 색인의 C10 순위다. Dense는 같은 보고서1,101개 청크 전체의 정확한 거리 순위이며 실제 검색은 상위16개만 후보로 가져온다. BM25는 상위24개, 최종 RRF는8개다.

| 출처 | 내용 | Dense 전체 순위 | BM25 전체 순위 | 최종 RRF |
| --- | --- | ---: | ---: | ---: |
| `395:290` | 연결 주당이익 표제만 | 1 | 132 | 3 |
| `400:295` | 연결 영업활동현금흐름 표제만 | 7 | 6 | **1** |
| `748:261` | 별도 영업활동현금흐름 표제만 | 10 | 7 | **2** |
| `401:296` | 연결 조정·자산부채 변동 상세값 | 108 | 762 | 후보 없음 |
| `104:5` | **요청한 연결 현금흐름표** | **31** | **3** | **8** |
| `486:4` | 별도 현금흐름표 | 25 | 4 | 10 |

C10의 Dense16개 중9개, 최종8개 중4개가 금액 없이 표제·기간·단위만 있는 청크다. 해당9개의 원문을 확인했으며, 일반적인 “숫자가 없다” 검사 결과를 모든 corpus의 불필요한 문서 판정으로 확장하지 않았다.

**BM25:** 원본 제목의 `COLSPAN=2`를 그리드로 복원하면서 `영업활동현금흐름`이 두 칸에 반복된다. 색인 접두어의 `table_row_labels`에도 한 번 더 있어 관련 bigram의 빈도가 올라간다. `400:295`는 BM25 토큰124개로 corpus 평균324.02보다 짧다. `금흐`, `흐름`, `현금` 등 실제 제목과 일치하는 토큰의 기여가 커서6위다. 쿼리 안의 반복 토큰도 현 tokenizer/scorer 계약대로 반복 가산된다. 토큰별 기여 합으로 실제 점수57.467068을 재구성했다. 공통 키워드 줄을 제거한 이전 비교에서도 두 표제의 BM256·7위는 그대로였다.

**Dense:** 저장된 원문 임베딩2,240개와 질문 임베딩12개를 원본 요청·응답에 다시 연결했다. 벡터의 잘못된 ID 연결·누락·비유한값은 발견하지 못했다. 기존 native top16은12문항 모두 정확한 L2 순위와 **192/192, 순서까지 일치**했다. C10 본표가31위인 것은 이 표본에서 ANN이 누락시킨 결과가 아니다. cosine으로 계산해도 본표31위, 두 표제7·10위여서 C10은 L2→cosine 교체만으로 해결되지 않는다.

표제 `400:295`의 임베딩 입력419자 중 원문은34자, 접두어는385자다. Dense가 이런 현재 표현의 표제 청크를 더 가깝게 평가한다는 것은 확인됐다. 그러나 **접두어·길이 각각이 Dense 순위에 미친 인과 효과는 새 임베딩 비교 없이 분리할 수 없다.** 다른 질문까지 거리 함수의 영향이 없다고 주장하지 않는다. C09·C11에서는 L2/cosine top16 집합이15/16으로 달랐다.

**RRF:** 후보 ID·점수·최종 입력12개를 재계산해 모두 재현했다. 구현 오류는 발견되지 않았다. 대신 현재 `k_rrf=60, Dense16, BM2524`에서는:

```
두 채널에 모두 있는 후보의 최소 점수 = 1/(60+16) + 1/(60+24) = 0.025063
한 채널에만 있는 후보의 최대 점수   = 1/(60+1)                = 0.016393
```

따라서 **두 채널에 모두 나온 후보는 한 채널에만 나온 후보보다 항상 앞선다.** C10에서 두 채널의 교집합은 바로 위 표제2개뿐이다. `400:295`는 `1/67+1/66=0.030077`로1위, `748:261`은 `1/70+1/67=0.029211`로2위가 된다. 요청한 본표는 Dense16 밖이라 BM25의 단일 점수만 받는다. 이전 접두어 제거에서 BM253→4위로 내려가자 최종8→10위로 탈락한 이유다. RRF의 일치 가산은 출처에 값이 있는지, 연결/별도 범위가 맞는지 확인하지 않는다.

## 검증과 판단

| 가설 | 이번 검증의 판단 |
| --- | --- |
| 파서가 필요한 숫자를 버렸다 | C10 본표에서는 관찰되지 않음; 원본과 값 보존 확인 |
| 긴 표를 청킹하다 표제만 잘렸다 | 추적한4쌍에서 배제; 원본부터 별도 TABLE, 각1청크 |
| 표제의 독립 색인이 관련됨 | 확인; 표제가 값0인 독립 문서로 임베딩·BM25 색인에 들어감 |
| 문맥은 구조화 데이터에 있으면 검색에서도 활용됨 | 성립하지 않음; 앞 표제·당기 문맥이 구조 객체에만 남는 경계 확인 |
| ANN·벡터 매핑 오류가 원인 | 이12문항 재현에서는 발견하지 못함 |
| 현재 Dense 관련성 순위에 문제가 있음 | C10에서 확인; 표제들을 먼저 고르고 본표는31위 |
| RRF 구현 버그 | 재현되지 않음; 계약의 중복 가산과 cutoff 효과 확인 |

원본2개를 동일 canonical 설정으로 재파싱해2,240개 원문·metadata 투영·색인 텍스트가 기존 자료와 일치했고 fallback0이었다. 새 구조 재현 테스트3개와 기존 문맥 보존 테스트10개가 모두 통과했다. 이는 현 동작의 재현이며 품질 개선의 증거가 아니다. 외부 호출0·비용0·runtime/store 변경0이다.

다음 수정의 우선 검토 지점은 **청크 크기나 RRF 상수보다, 물리적으로 연결된 표제와 값 표를 검색 단위에 어떻게 표현할지**다. 임의 제목을 허용 목록에 추가하거나 모든 인접 표를 합치기 전에, 원본 연결·기간·단위 보존과 독립 표제의 검색 역할을 함께 정해야 한다. 이번 사례처럼 인접 값 표가 질문의 피연산자를 포함하지 않을 수 있어 실제 근거 충분성과 다른 문항의 회귀를 별도로 검증해야 한다. 이 진단에서 수정안·새 임베딩·정확도 실험은 실행하지 않았다.

재현 자료는 Git ignored인 `benchmarks/results/header_chunk_origin_audit_2026-10-15/`에 있다. `scope.json`, `freeze.json`, `source_lineage.json`은 원본 byte/XPath→블록→청크→색인 텍스트를, `retrieval_audit.json`은 전체 Dense 순위·토큰별 BM25 기여·RRF 계산을, `findings.json`과 `characterization_checks.json`은 판정 및13개 테스트 결과를 담는다. `closeout.json`은 기존 실험·보호 파일·최종 문서의 무결성을 연결한다. 비맹검 assistant 검토이며 일반 모델 성능이나 전체 parser 정확도에 대한 판정은 아니다.
