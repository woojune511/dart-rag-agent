# 질문 분해 검색의 근거 충족과 답변 성능 실험 설계

설계일: 2026-10-20. 상태: **설계 완료, 실행 전**. 이 문서는 기존 12문항으로 수행할 작은 진단 실험과, 통과했을 때의 새 문서 검증을 정의한다. 이번 작업에서는 런타임 수정, 검색, 모델 호출, store 복사·변경을 하지 않았다. 아래 비용은 제안 상한이며 실행 승인이나 실제 지출액이 아니다.

검증할 가설은 **복합 질문의 요구사항을 검색용 하위 질문으로 나누면, 같은 최종 문맥 한도에서 필요한 근거가 더 많이 모이고 완전하고 정확한 답변이 늘어난다**는 것이다. 단순히 문맥을 늘리거나 원래 질문으로 더 깊이 검색한 효과와 구분한다. 기본 앱의 `SimpleRagAgent`는 그대로 두고 명시적 실험 경로만 사용한다.

## 1. 이 가설을 선택한 근거

- [현재 v12 전체 평가](full77_v12_final_result_2026-10-18.md)에서 공통 판정 가능 48문항의 종합 통과는 과거·현재 모두 30/48이었다. 현재 실패 18개 중 12개는 전달 근거가 부분적이거나 없었고, 6개는 근거가 충분해도 실패했다. 검색 개선과 독해 개선을 분리할 이유다.
- [과거 v9 문맥 크기 비교](new18_v9_rrf_window_answer_result.md)에서는 동일 후보 순위의 top-8을 top-12로 넓혔을 때 엄격 통과가 23/36→26/36이었다. 18문항의 두 번 반복 결과이며, 현재 v12나 새로운 질문에서의 효과는 아니다. 따라서 이번에도 문맥 확대를 별도 비교군으로 둔다.
- [Ammann 등의 ACL 2025 연구](https://aclanthology.org/2025.acl-srw.32/)는 질문 분해, 검색 결과 결합, 재순위화를 함께 평가했다. 이번에는 학습·reranker 없이 분해와 순위 결합을 검증한다. 논문의 전체 방법을 재현하거나 그 개선폭을 기대값으로 사용하지 않는다.
- [Xie 등의 NAACL 2025 연구](https://aclanthology.org/2025.naacl-long.301/)는 핵심 하위 질문의 충족을 평가하고 검색 개선에 사용한다. 여기서는 정답 문자열 일치보다 요청별 근거 충족을 중간 지표로 삼는 근거로 활용한다. 평가용 요구사항을 검색기에 넣지는 않는다.

## 2. 비교 조건

| 조건 | 검색 질문 | Dense / BM25 후보 한도 | 최종 선택 | 구분하려는 효과 |
|---|---|---|---:|---|
| A 현재 기준 | 원래 질문 1개 | 16 / 24 | 8 | 현재 방식 |
| B 문맥 확대 | A와 정확히 같은 후보 목록 | 16 / 24 | 12 | 후보를 고정한 문맥 개수 효과 |
| C 질문 분해 | 원래 질문 + 최대 2개 하위 질문 | 질문마다 16 / 24, 합계 최대 120 슬롯 | 12 | 여러 검색 질문과 순위 결합의 효과 |
| D 검색 깊이 확대 | 원래 질문 1개 | 48 / 72, 합계 최대 120 슬롯 | 12 | 같은 최대 후보 슬롯을 원래 질문에 사용한 효과 |

**주 비교는 C 대 D**, 제품 기준 비교는 C 대 A다. B 대 A는 문맥 확대, D 대 B는 원래 질문의 검색 깊이 확대를 보여 준다. C가 B만 이기고 D와 비슷하면 질문 분해의 추가 복잡성이 필요하다는 근거가 부족하다.

슬롯 수는 중복 제거 전 각 검색 목록의 위치 수다. BM25의 양수 점수가 적거나 중복 문서가 있으면 실제 후보 수는 더 작다. C에 하위 질문이 0~1개만 나오면 후보 한도도 줄어든다. D와 C는 **최대 후보 슬롯**을 맞춘 비교이며, 실제 고유 후보 수·연산량·토큰·비용까지 같다는 뜻은 아니다. 이를 각각 기록한다.

모든 조건의 답변 입력 한도는 기존 **65,536 UTF-8 bytes**다. 원래 질문·명시적 scope·source metadata까지 포함하는 기존 packet 규칙을 사용한다. source를 통째로 생략하고 본문을 자르지 않는다. 12개 선택이 12개 전달을 보장하지 않으므로 선택 목록과 실제 전달 목록을 따로 평가한다.

### 현재 API에서 주의할 점

[`VectorStoreManager.search`](../../src/storage/vector_store.py)는 `k`를 최종 개수와 후보 깊이에 함께 사용한다. Dense는 `2*k`, [`collect_bm25_results`](../../src/storage/bm25_index.py)는 최대 `3*k`다. 따라서 `agent.k=12`만 설정하면 B가 아니라 Dense24/BM25 최대36이라는 다른 실험이 된다.

실험 어댑터는 후보 깊이와 최종 선택 수를 분리한다. A의 Dense16/BM25 최대24를 한 번 저장하고 B 및 C의 원래 질문 부분에 재사용한다. D의 Dense48은 같은 원래 질문 embedding으로 별도 조회한다. 근사 최근접 검색에서는 top-48의 앞 16개가 직접 top-16과 같다고 가정하지 않는다. A를 D의 앞 16개로 재구성하지 않고 실제 목록을 각각 보존한다.

## 3. 질문 분해와 결합 방법

분해 모델은 답변 모델과 같은 `gpt-5.6-terra`, reasoning `low`로 고정한다. 질문당 한 번만 분해하고 결과를 저장한다. 최대 출력은 1,024 tokens이며 답변 생성과 구분해서 계측한다. 분해 입력은 **원래 질문만**이다. 정답, 요구사항 표, 평가 ID, 과거 실패 설명, 문서 내용, 정답 source ID는 넣지 않는다.

분해 system prompt 초안은 아래 하나로 고정하며, 실행 전 최종 SDK schema와 함께 해시를 남긴다. 예시 문항은 넣지 않는다.

```text
사용자 질문에 명시된 정보 요구를 검색할 수 있는 하위 질문을 최대 2개 작성하세요.
각 하위 질문은 독립적으로 검색할 수 있어야 합니다. 서로 다른 요구를 우선하고,
같은 질문의 표현만 바꾼 중복 검색어나 원래 질문 전체의 재진술은 만들지 마세요.
질문에 있는 주체, 기간, 비교 기준, 범위와 한정 조건을 보존하세요.
질문에 없는 사실, 답, 수치, 원인 또는 관계를 추측해서 추가하지 마세요.
계산 요청에서는 답을 계산하지 말고 필요한 원문 정보를 찾도록 작성하세요.
별도로 검색할 요구를 나눌 필요가 없으면 빈 배열을 반환하세요.
각 하위 질문은 256자 이내로 작성하고 지정된 JSON 형식만 반환하세요.
```

출력은 추가 속성이 없는 `{"subqueries": ["..."]}`이며 문자열 0~2개만 허용한다. 빈 문자열·길이·schema 위반은 실패로 남기고 재시도하지 않는다. 공백 정리와 동일 문장 중복 제거만 허용하며 원래 질문과 같은 하위 질문도 제거한다. 의미가 잘못된 분해를 사람이 고치거나 여러 출력을 생성해 고르지 않는다. 잘못된 의미 해석 자체가 실험 결과다.

검색 순서는 원래 질문, 첫 하위 질문, 두 번째 하위 질문이다. 모든 검색에 caller가 지정한 같은 `rcept_no` filter를 적용한다. 분해 모델은 scope를 변경하지 못한다. 질문의 연도를 metadata filter로 바꾸지 않는다. 원래 질문은 항상 포함되며, 답변 모델에는 **원래 질문과 최종 source packet만** 제공한다. 하위 질문이나 분해 과정의 추론은 답변 prompt에 넣지 않는다.

결합은 기존 RRF의 상수 60을 유지한다. 검색 질문 수를 m, 각 질문의 Dense/BM25 순위를 r이라고 하면 C의 점수는 다음과 같다.

```text
score(d) = (1/m) * sum over query i of
           [1/(60 + dense_rank_i(d)) + 1/(60 + bm25_rank_i(d))]
```

목록에 없는 문서의 항은 0이다. 각 질문에서 먼저 top-8로 잘라 버리지 않고 전체 후보 순위를 결합한다. 원래 질문과 하위 질문의 가중치는 같고, 별도의 다양성 보너스·coverage selector·reranker는 없다. m=1이면 B와 같은 점수·순서·packet이어야 한다. `/m`은 같은 질문 안에서 순위를 바꾸지 않는다.

중복 제거는 기존 [`doc_identity`](../../src/storage/search_merge.py)를 따르되 보고서 범위와 동일 ID의 본문·문맥 일치를 검증한다. 동점은 기존 stable ordering을 유지한다. 삽입 순서는 질문 순서, 각 질문의 Dense 순서, BM25 순서다. A/B/D도 기존 Dense→BM25 삽입 순서를 유지한다. 조건마다 다른 사후 tie-break를 넣지 않는다.

이 실험의 처치는 **질문 분해와 다중 질문 순위 결합의 묶음**이다. 두 요소 각각의 독립 기여나 적응형 반복 검색의 효과까지 주장하지 않는다.

평가 기준은 원래 질문, 원본 `answer_key`·`eval_checkpoints`, 기존 `criteria.json`, [평가 계약 처분](evaluation_contract_disposition_v1.md)을 함께 사용한다. `required_entities` 키워드 일치나 특정 chunk ID 적중만으로 정답 처리하지 않는다. 특히 `SKH_T1_060`은 기존 기준대로 명시 항목 합계와 유동성 대체를 포함한 총차입금 해석을 모두 허용하되, 선택한 범위를 밝히고 일치하는 자산 분모를 사용해야 한다.

실행 전 원문과 저장 source로 각 답변 가능 문항의 필수 근거 단위를 확정한다. 단위마다 주체·기간·범위·값·단위 또는 관계·원문 위치와 허용되는 대체 근거를 기록한다. 예를 들어 두 피연산자가 있어도 기간이 다르거나 표의 단위가 빠지면 완전한 근거로 세지 않는다. 숫자 자체를 찾는 것과 그 숫자의 축을 확인하는 것을 구분한다. 이 작업은 provider 없이 하고, C의 검색 결과를 보기 전에 동결한다.

## 5. 단계별 실행과 중단 기준

### 단계 0 준비와 외부 호출 없는 검증

현재 HEAD는 `1d09627d8ec79ab29c337d31bcb1a4f5aae9251b`이지만 미커밋 v12 소스가 존재한다. 실행 시점의 소스·실험 어댑터·prompt·schema·패키지·store 파일·질문·평가 기준 해시를 함께 고정한다. HEAD만으로 실행 버전을 표현하지 않는다.

기존 v12 store의 무결성을 확인한 별도 실험 복사본만 사용한다. canonical ingest는 `structural_selective_v2_prefix_2500_320`, parser는 `financial_parser_v12_schema_literal_labels`, collection은 `dart_reports_v12_full11_2023`이다. 새 ingest·문서 embedding·parser 수정·caption 연결·실험 lexical policy·Compiler는 제외한다. 활성 앱 store는 평가 client로 열지 않는다.

구현 전 [`agent_runtime_contract.md`](../architecture/agent_runtime_contract.md)와 [`codebase_map.md`](../overview/codebase_map.md)를 따른다. 후보 수와 답변 packet을 분리하는 실험 어댑터 외의 구조 변경은 범위에 없다. 다음 계약을 mock과 고정 fixture로 확인한 뒤 실행 manifest를 봉인한다.

1. A는 기존 `search(k=8)`의 후보·RRF·실제 packet과 일치하고, B는 같은 후보에서 12개만 선택한다.
2. C의 원래 질문 후보는 A와 같고, 하위 질문이 없으면 C와 B가 동일하다. 하위 질문당 후보 한도를 넘지 않는다.
3. D의 후보 한도, 모든 조건의 filter, ID 충돌 거절, 동점·중복 처리, 전체 source 생략 규칙이 맞는다.
4. SDK 입력에 정답·평가 ID·평가용 source 목록이 없으며 답변 입력에는 원래 질문만 사용한다.
5. 모든 provider retry가 0이고, 한도 초과·HTTP 오류·usage 누락·schema 실패 시 새 호출을 차단한다. count endpoint와 자동 judge 호출도 0이다.
6. 재생 어댑터를 통한 답변 생성에 숨은 재검색·embedding이 없고, 실제 다중 query trace를 별도 저장한다. 기존 SimpleRagAgent의 단일 query trace만으로 C를 설명하지 않는다.

준비 중 필수 원문 근거를 확정할 수 없으면 돈을 쓰기 전에 `PREPARATION_BLOCKED`로 남긴다. 문항을 조용히 교체하거나 gold를 고쳐 현재 버전을 유지하지 않는다. 필요하면 새 설계 버전으로 이유를 기록한다.

### 단계 1 검색과 실제 전달 근거 평가

12개 질문을 각각 한 번 분해한다. 원래 질문 embedding은 A/B/C/D가 공유하고, 유효한 하위 질문만 추가 embedding한다. 원래 질문의 좁은·깊은 후보와 각 하위 질문 후보를 저장한 뒤 네 조건의 packet을 기존 직렬화 규칙으로 만든다. 이 단계에서는 답변을 생성하지 않는다.

평가용 필수 근거 전체가 있는지를 **후보 합집합 → 최종 선택 → 실제 packet**의 세 위치에서 각각 판정한다. 검색어 단위나 특정 정답 ID만 보지 않고 유효한 대체 근거를 인정한다. 필요한 근거가 후보에만 있고 packet에 없으면 답변 단계의 coverage 개선이 아니다.

다음을 모두 만족해야 단계 2로 간다.

- 목표 6문항에서 C의 실제 packet이 D보다 완전한 근거를 제공하는 문항이 순증 2개 이상이며, 개선 문항이 서로 다른 회사 2개 이상에 걸쳐 있다.
- 같은 목표 6문항에서 C가 A보다 완전한 근거를 제공하는 문항도 순증 2개 이상이다.
- 성공 통제 3문항에서 A가 제공한 필수 근거를 C가 잃는 사례가 없다.
- scope 누출, source 변조, 설정·예산 위반이 없다.

충족하지 않으면 `NO_EVIDENCE_GAIN`으로 종료한다. 답변 생성 96회를 자동 실행하지 않으며, 같은 패널에서 분해 prompt·가중치·후보 수를 바꿔 다시 시도하지 않는다. 후보 단계만 개선됐으면 최종 선택 병목으로 기록한다. 이 gate는 이 실험의 근거 충족 가설에 대한 실용적 중단 규칙이며, 모든 질문 분해 방법의 무효를 뜻하지 않는다.

### 단계 2 동일 packet의 답변 비교

12문항 × 4조건 × 2반복 = **최대 96개 새 답변**을 생성한다. 질문별 분해 결과와 retrieval packet은 두 반복에 재사용하고, 답변 호출만 두 번 한다. 이 실험은 생성 변동을 일부 관찰하지만 분해 변동까지 추정하지 않는다.

답변은 기존 `SimpleRagAgent`의 원래 `ANSWER_INSTRUCTIONS`·`RagAnswer`, `gpt-5.6-terra`, reasoning `low`, 최대 출력 8,192 tokens를 유지한다. 생성 retry 0, timeout 90초, default tier, `store=false`를 사용한다. 원래 응답의 산술 `not_executed`, 의미 지지·요청 충족 `not_checked`도 유지한다. 사후 평가를 제품의 자동 검증 기능으로 표시하지 않는다.

호출 순서는 위 패널 순서로 질문마다 네 조건을 교차 배치한다. 0부터 시작하는 질문 번호 i에서 1회차는 `[A,B,C,D]`를 i mod 4만큼 회전하고, 2회차는 같은 순서를 두 칸 더 회전한다. 한 조건을 모두 끝낸 다음 다른 조건을 실행하지 않는다. 동시 호출은 1개다. 원래 source가 하나도 전달되지 않으면 기존 무근거 응답을 사용하고 생성 횟수는 줄이며, 유리한 재검색을 하지 않는다.

출력은 조건 이름을 가린 식별자로 섞어 원문·packet·인용과 대조한다. 평가는 아래 기준을 먼저 적용하고 mapping은 판정 저장 후 연다. 같은 작성자가 검토한다면 독립 사람의 blind 평가라고 부르지 않는다. 자동 모델 judge는 추가하지 않는다.

## 6. 지표와 판정

### 주 지표

답변 가능 10문항은 **정확성·필수 요구 충족·인용 근거 지지가 모두 PASS**일 때만 성공이다. 필요한 항목을 유보한 부분 답변은 안전할 수 있어도 완전 성공이 아니다. 필수 정답뿐 아니라 추가로 한 중요한 사실 주장도 검토한다.

문항별로 0/2, 1/2, 2/2 성공을 보고한다. 평균 성공률은 `문항별 성공 횟수/2`의 평균이며, 20개 출력을 독립 문항처럼 다루지 않는다. 안정적 개선은 비교군 0/2→C 2/2, 안정적 회귀는 비교군 2/2→C 0/2다. 1/2가 포함된 변화도 별도로 보존한다.

거절 2문항은 별도 분모다. 잘못된 사실을 만들지 않고, 전달 근거에서 확인할 수 있는 범위를 밝혀야 한다. 전체 보고서 부재를 packet 부재만으로 단정하면 통과시키지 않는다. 거절을 많이 해서 답변 가능 문항의 정확도가 오른 것처럼 표현하지 않는다.

### 중간 지표와 비용

| 지표 | 기록 방법 |
|---|---|
| 필수 근거 충족 | 후보·선택·실제 packet에서 모든 필수 단위 충족 여부; 단위별 부분 충족도 별도 |
| 오류 위치 | 분해 의미 변경, 후보 누락, 순위 탈락, byte 제한 생략, 근거 충분 독해 실패 |
| 주장 회귀 | 주체·연도·연결/별도·단위·인과·관계 오독 및 근거 없는 추가 주장 |
| 검색량 | 각 query의 Dense/BM25 순위와 점수, 중복 전 슬롯·고유 후보·실제 전달 source 수 |
| 입력량 | 실제 packet bytes, 입력 tokens, 생략 source와 사유 |
| 비용 | 분해·embedding·답변별 usage; 일반/캐시 입력, reasoning/비 reasoning 출력 구분 |
| 시간 | 분해, 각 검색, packet 생성, 답변의 계측 시간; 전체 실험 wall time 별도 |

실제 지출과 배포 시 예상 조건별 비용을 구분한다. 공유한 원래 embedding을 D에 0원으로 배정하지 않는다. 조건별 질문당 비용은 필요한 embedding 전체 + C의 분해 1회 + 두 답변 비용의 평균으로 계산한다. 두 반복 때문에 분해 비용을 절반으로 줄이지 않는다. C의 온라인 지연 추정도 분해·원래/추가 검색·답변의 시간을 모두 포함한다. 저장 packet 재생 시간만으로 실서비스 응답시간을 주장하지 않는다.

### 1차 실험 통과 기준

새 문서 검증으로 진행하려면 다음을 모두 만족해야 한다.

1. C 대 D의 안정적 개선−안정적 회귀가 최소 +2문항이고, 개선이 최소 2개 회사에 걸쳐 있다.
2. C 대 A도 안정적 개선−안정적 회귀가 최소 +2문항이다. B와의 차이 및 문항별 평균 성공률도 함께 공개한다.
3. 성공 통제 3문항에서 C의 성공 횟수가 A보다 줄지 않고, 거절 통제 2문항에서 새 실패가 없다.
4. 기존 실패 문항 안의 악화를 포함해 A 또는 D 대비 C에 새로 생긴 중대한 미지원 주장이 없다. 전체 pass 수가 같아도 이런 회귀를 숨기지 않는다.
5. 조건별 질문당 평균 비용 C/A가 2.0배 이하이고, 구성 단계로 추정한 중앙 응답시간 C/A가 2.5배 이하다.

이 수치는 미리 정한 작은 실험의 진행 기준이다. 통계적 유의성, 일반 정확도 개선, 기본 앱 채택의 기준을 충족했다는 뜻은 아니다. 답변만 좋아지고 근거 충족이 그대로면 retrieval 가설의 증거와 분리한다. 단계 1은 통과했지만 답변 이득이 없으면 `EVIDENCE_GAIN_WITHOUT_ANSWER_GAIN`으로 종료한다.

새 gold 충돌은 원래 판정과 근거를 남겨 `UNJUDGEABLE`로 표시한다. 해당 문항을 분모에서 빼 통과 기준을 쉽게 만들지 않는다. 판정 불가를 개선에 포함하지 않는 보수적 하한도 함께 제시하고, 주요 개선 문항의 판정이 보류되면 최종 결정은 `INCONCLUSIVE`다. HTTP/구현/설정 실패는 성능 실패와 분리하여 `INVALID_RUN` 또는 `NOT_RUN`으로 남긴다.

## 7. 호출과 비용 상한

| 구분 | 단계 1 최대 | 단계 2 추가 최대 | 합계 최대 |
|---|---:|---:|---:|
| 분해 생성 | 12 | 0 | 12 |
| query embedding | 36 | 0 | 36 |
| 답변 생성 | 0 | 96 | 96 |
| 실제 provider HTTP 시도 | 48 | 96 | **144** |

embedding은 문자열당 한 요청으로 고정하고 원래 질문을 조건 간 공유한다. 모든 SDK/transport retry는 0이다. 유효 하위 질문이 적거나 무근거 응답이면 실제 호출은 줄어든다. server token count, judge, fresh ingest, 문서 embedding, 다른 모델 probe는 이 예산에 포함되지 않으며 이번 실행에서는 허용하지 않는다.

**제안 비용 상한은 단계 1 USD 2, 전체 누적 USD 30**이다. 이는 실제 예상 요금이 아니라 호출 전 차단에 사용할 최대 허용액이다. 실행일의 공식 가격을 확인해 고정하고, 현재 admission 방식의 입력 상한 및 최대 출력으로 예약 비용을 산출한다. 캐시 할인은 상한 계산에 의존하지 않는다. 두 단계 전체의 보수적 사전 한도가 USD 30을 넘거나 단계 1 한도를 만족하지 못하면 호출 전 중단한다. 자동으로 예산·모델·출력 한도를 바꾸지 않는다.

외부 호출 단계에는 20초 heartbeat, 총 provider 실행 wall time 30분 상한을 둔다. 원문 검토 시간은 이 실행 시간에서 분리한다. 첫 HTTP 오류·timeout·불완전 응답·schema 오류·usage 누락·scope 위반·source 충돌·설정 drift·예산 초과 시 중단한다. 이미 시작한 요청은 취소·재시도로 증식시키지 않고 보수적으로 정산하며, 남은 셀은 `NOT_RUN`이다. 기록은 유지하고 새 디렉터리에서의 재실행 여부는 별도 작업으로 판단한다.

## 8. 성공 후 새 문서 검증

1차 결과만으로 “DART RAG의 정확도를 높였다”고 일반화하지 않는다. 통과하면 분해 prompt·fusion·예산·모델·평가 기준을 고정한 채, 개발에 사용하지 않은 회사와 보고서에서 새 질문을 만든다. 같은 문항의 표현만 바꾸거나 정답 문장을 질문에 복사하지 않는다.

후속 검증의 시작 규모는 **새 회사 6개·보고서 6개·60문항**으로 제안한다. 보고서마다 복합 요구 6개, 단일 목표 2개, 답할 수 없는 요청 2개를 구성한다. 가능하면 기존 기간과 다른 보고서도 포함하고, 회사·보고서 단위로 이전 평가와의 중복을 감사한다. 적합한 원문과 store 확보 비용은 새 실행 설계에서 산정하며 현재 144회·USD 30 범위에 합치지 않는다.

조건은 A/C/D, 답변은 두 번 반복한다. 현재 기준 대비 실용 이득 C−A와 후보 깊이 통제 대비 C−D를 함께 확인한다. 질문과 근거는 모델 출력을 보기 전에 작성·검토·봉인하고, 검토자는 조건명과 검색 가설을 보지 않게 한다. 독립 검토자를 확보하지 못하면 자체 평가임을 명시한다.

60문항은 고정된 검정력 보장이 아니다. 이 패널은 보고서별 질문이 서로 연관되므로 질문/반복을 모두 독립 표본으로 취급하지 않는다. 실행 전 최소 관심 개선폭과 표본 수를 확정하고, 보고서별 결과·문항별 paired 차이·불확실성을 함께 보고한다. 작은 폭의 차이나 넓은 불확실성은 결론 보류로 남기고, 결과를 본 뒤 좋은 문항만 추가하거나 제외하지 않는다. 새 문서 검증 전에는 기본 경로를 바꾸지 않는다.
