# 추가 LLM 선택 호출의 필요성: 저장 결과 감사

Date: 2026-09-29. Status: **COMPLETE_OFFLINE_NOT_ADOPTED**.

추가 선택이 도움을 준 입력은 있지만, 호출 전에 이를 안정적으로 구분하는
규칙은 확인하지 못했다. 검색 순위 불일치 규칙 하나가 별도 12문항에서는
좋은 저장 결과를 골랐으나, 개발 표본에서는 개선을 많이 놓치고 근거 회귀도
선택했다. 제품에 조건부 호출을 도입하지 않는다.

## 무엇을 평가했는가

새 LLM 호출 없이 기존 두 실험의 질문별 RRF 답변과 선택 후 답변을 조합했다.

- 개발 표본: [고정 후보 비교](fixed_pool_selection_result.md)의 6문항 ×
  flat/table, 12개 입력. 과거 성공/실패를 의도적으로 골랐고 두 표현은 같은 문항이다.
- 별도 표본: [새 문항 비교](semantic_selection_new_questions_result.md)의
  N01–N12. 익숙한 보고서에서 작성한 문항이며 결과는 이미 노출돼 있다.
- 두 표본을 하나의 24문항 정확도로 합치지 않는다. 이번 분석도 독립 holdout이나
  블라인드 평가가 아닌 **사후 분석과 표본 간 규칙 적용**이다.
- 주 지표는 정확·완전·인용 지지 통과 및 `abstained=false`다. 이전 고정 후보
  실험의 엄격 통과 10/12에서 과도한 거절 1개를 제외하므로 이 보고서는 9/12를 쓴다.
  내용·근거 충분성·비거절을 혼동하지 않도록 보조 지표도 별도 집계했다.

## 사후에 최선의 경로를 고를 수 있었다면

`사후 최선`은 RRF가 실패하고 선택 후 답변이 통과한 입력만 추가 선택한다.
양쪽이 같으면 RRF를 사용한다. 모든 관측 입력에서 선택 경로의 비용이 더 크므로,
이 방식은 저장된 최대 통과 수를 얻으면서 호출 수와 추정 비용을 최소화한다.

**두 단회 응답 중 좋은 것을 골라 만든 상한**이다. 실제로 구현할 수 있는
판별기나 재실행 시 유지되는 인과적 성능 상한은 아니다. 정답을 알아야 하는
선택 정보를 runtime에 제공하지 않는다.

| 표본 | 경로 | 주 지표 통과 | 추가 선택 호출 | 저장 사용량 기준 추정 USD |
| --- | --- | ---: | ---: | ---: |
| 개발 12입력 | 항상 RRF | 3/12 | 0 | 0.378911 |
| 개발 12입력 | 항상 선택 | 9/12 | 12 | 1.530363 |
| 개발 12입력 | 사후 최선 | 9/12 | 6 | 0.975469 |
| 개발 12입력 | 순위 불일치 규칙 | 5/12 | 4 | 0.830838 |
| 별도 12문항 | 항상 RRF | 11/12 | 0 | 0.256140 |
| 별도 12문항 | 항상 선택 | 11/12 | 12 | 1.067338 |
| 별도 12문항 | 사후 최선 | 12/12 | 1 | 0.307849 |
| 별도 12문항 | 순위 불일치 규칙 | 12/12 | 2 | 0.416701 |

별도 표본에서 얻을 수 있었던 최대 추가 통과는 **1개**다. 사후 최선도 항상
RRF보다 약 20.2% 비싸다. 순위 규칙은 약 62.7% 비싸지만 항상 선택보다 약
61.0% 저렴하다. 이 수치는 현재 가격 견적이나 관측 청구액이 아닌 기존 receipt의
추정 비용 재합산이다. 실제로 이번 비용을 지출한 것은 아니다.

가상 비용은 각 문항에서 **RRF 답변 또는 선택+선택 후 답변** 중 하나만 센다.
별도 표본의 공통 질문 임베딩 비용은 어느 경로에도 한 번 포함한다. 개발 표본은
저장 검색 결과를 사용했으므로 이전 검색·임베딩 비용이 포함되지 않는다.
두 패널의 비용을 직접 비교하지 않는다. 저장된 단계 시간 합도 JSON에 남겼지만
새 실행의 지연이나 wall-clock 시간으로 해석하지 않는다.

## 호출 전에 계산할 수 있는 신호 하나

Dense와 BM25의 각각 상위 8개 ID 집합을 사용했다.

`불일치 = 1 − 교집합 크기 / 합집합 크기`

개발 표본의 **정답을 사용하지 않은 중앙값 6/7**을 경계로 정했다. 불일치가
그 값보다 클 때만 호출한다. 이번처럼 각 목록에 서로 다른 ID가 8개씩 있으면
공통 후보가 0–1개일 때 호출하는 것과 같다. 경계와 같으면 호출하지 않는다.
동일한 경계를 별도 표본에 적용했고, 다른 경계를 탐색하거나 결과에 맞춰 조정하지 않았다.

규칙·표본·지표를 먼저 고정하고, 특징과 경계를 저장한 뒤 코드가 판정 파일을
읽게 했다. 그러나 작성자는 이전 결과를 알고 있었으므로 완전한 설계 블라인드를
주장하지 않는다. 회사·질문 ID·문항 유형·정답·witness·답변 확신·모델 충분성 선언은
호출 신호로 쓰지 않았다. ID는 출처 집합의 동일성 비교에만 쓰인다.

후보 수, 기존 top-8의 연결/별도 범위, 저장된 기간 표시도 설명용으로 기록했지만
추가 규칙을 학습하지 않았다. Flat의 기간 표시 누락은 기간 혼동이 없다는 뜻이 아니다.

| 주 지표 기준 호출 판단 | 개발 12입력 | 별도 12문항 |
| --- | ---: | ---: |
| 개선 입력을 호출함, TP | 2 | 1 |
| 개선 없는 입력도 호출함, FP | 2 | 1 |
| 개선 입력을 놓침, FN | 4 | 0 |
| 개선 없는 입력은 건너뜀, TN | 4 | 10 |

이것은 **저장된 추가 선택의 이득 탐지** confusion matrix다. 답변 가능/불가능
분류가 아니다. FP에는 두 경로 모두 실패하거나 근거는 개선돼도 거절 플래그가
남은 경우 등이 포함되므로, 모든 FP가 새 오답을 만들었다는 뜻도 아니다.

## 왜 좋은 별도 표본 결과만으로 채택하지 않는가

- 별도 표본에서는 N02와 N05만 호출한다. N02의 연도 해석 개선은 잡고 N12의
  rubric상 누락 회귀는 피한다. N05는 양쪽 모두 통과하여 추가 비용만 발생한다.
- N02는 **RRF에도 필요한 근거가 이미 있었다**. 따라서 규칙이 근거 부족을
  정확히 발견했다고 설명할 수 없다. 선택 호출·답변 context·단회 생성 결과가
  함께 달라진 사례다. 우연한 답변 변동을 분리할 반복 관측도 없다.
- 개발 표본에서는 주 지표 개선 6개 중 2개만 잡는다. SKH 외환 flat, Celltrion
  북미 flat처럼 선택이 도움을 준 입력에서도 두 검색 목록은 더 많이 겹쳤다.
  검색기 간 합의는 필수 근거가 top-8에 있다는 보증이 아니다.
- 개발 SAM 재고 flat은 불일치가 커서 호출하지만 당기 근거를 버리는 회귀가 난다.
  RRF도 인용 문제로 주 지표 실패였기에 주 지표에는 새 회귀로 나타나지 않는다.
  **핵심 내용과 근거 충분성에서는 명확한 1건 회귀**다.

| 개발 표본 보조 지표 | 항상 RRF | 항상 선택 | 지표별 사후 최선 | 순위 규칙 |
| --- | ---: | ---: | ---: | ---: |
| 핵심 내용 | 6/12 | 11/12 | 12/12 | 7/12 |
| 전달 근거 충분성 | 6/12 | 11/12 | 12/12 | 7/12 |
| 엄격 지지 통과, 거절 허용 | 3/12 | 10/12 | 10/12 | 6/12 |

각 보조 지표의 사후 최선은 그 지표에 맞춰 경로를 따로 고른 값이다. 단일
oracle 경로가 모든 지표의 최대치를 동시에 얻는다고 주장하지 않는다.

별도 표본의 전달 근거는 모든 경로에서 12/12 충분하다. N12에서 질문에 직접
열거한 항목만 요구하는 기존 민감도를 적용하면 항상 선택도 12/12가 되어
회귀 1개는 사라진다. 순위 규칙은 그 경우에도 12/12다. 고정 rubric 주 판정을
사후에 바꾸지 않았다.

두 패널의 모든 입력은 적어도 한 경로에 충분한 근거가 전달된 것으로 기존
원문 검토가 판단했다. 따라서 **후보 전체에 근거가 없는 상황 0개**이며 그런
상황을 감지하는 능력은 평가할 수 없다. 기존 DRAM 대표 witness의 잘못된
원재료 비중 주석은 이번 특징에 쓰지 않았고, 옛 점수를 재평가하지도 않았다.

## 결론과 산출물

“LLM이 필요함”을 하나의 참/거짓 상태로 판정하기보다, **추가 호출의 기대
이득을 비용·근거 회귀와 함께 예측할 수 있는가**가 정확한 문제다. 이번 저장
표본에서 사후 이득은 존재하지만, 검색 순위 불일치 하나는 안정적인 판별 근거가
되지 못했다. 기본 SimpleRagAgent를 유지하고 자동 router를 도입하지 않는다.

이 신호를 다시 평가한다면 규칙을 그대로 둔 채, 새 질문과 후보 근거 부족
사례를 포함해 반복 생성의 변동을 확인해야 한다. 그 검증과 유료 실행은 이번
작업에 포함하지 않았다. 다른 신호를 결과에 맞춰 계속 탐색하지 않았다.

로컬 산출물: `benchmarks/results/selector_call_audit_2026-09-29/`.

- `profile.json`, `audit.py`: 범위·지표·규칙·집계 코드.
- `frozen_gate.json`, `precall_features.json`: 판정 파일을 읽기 전에 저장한 특징·경계.
- `paired_rows.json`, `analysis.json`: 24개 입력의 기존 판정·메모·비용 및 대응 집계.
- `check.py`, `test_results.txt`: 네트워크 차단 계약 테스트 **9개 통과**.
- `input_seal.json`, `analysis_seal.json`, `verification.json`, `completion_seal.json`:
  기존 소스·결과·외부 검색 trace 등 **1,204개** 입력 보호 및 최종 무결성 기록.

Provider·임베딩·새 수집 0회, 실제 router 실행·새 모델 품질 평가는 NOT_RUN이다.
원본 파일은 보존했으며 current 문서만 의도적으로 갱신했다. 예전 completion
seal에 포함된 current 문서까지 갱신 후에도 같은 hash라고 주장하지 않는다.
생성기는 기존 파일 덮어쓰기를 거절한다.
