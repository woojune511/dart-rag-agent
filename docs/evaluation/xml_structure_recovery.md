# 차단 원문 4개 원인 진단과 문자 경계 복구

2026-10-16. **3개 복구·1개 차단 유지.** v10 XML 오류 차단을 유지하면서 sanitizer의 문자 `<` 처리 경계만 수정했다. 원본 파일, 기존 저장소, 과거 평가 결과를 변경하지 않았다.

원문에 문제가 있었던 것 외에 **기존 전처리가 정상인 다음 태그를 훼손한 결함**이 세 파일에 공통으로 있었다. 과거 복구 모드에서는 첫 오류 뒤 정상 entity 문자까지 누락됐다. 모든 보고서에서 큰 본문 구간이 통째로 사라졌다는 결론은 아니다.

수정 전 오류·원문 대조 (`../../benchmarks/results/xml_structure_recovery_2026-10-16/before_diagnosis.json`, local artifact not included)는 전처리 XML의 행·열과 실제 전후 문자열을 보관한다. 정확한 LF 기준으로 읽어 Unicode 줄 구분자가 위치를 바꾸지 않게 했다.

## 수정 범위

`_sanitize_xml_like_text`에 문자 경계 조건 하나를 추가했다. 완전한 태그가 아니며 첫 문자가 기존 지원 태그 문법의 시작도 아니고, 다음 `<`가 먼저 나타나면 현재 문자 `<`만 `&lt;`로 보존하고 다음 태그에서 다시 읽는다. 뒤의 정상 태그, 본문, 속성값, 줄바꿈은 그대로 둔다.

회사명·질문ID·재무 용어·문제 태그 이름을 runtime 조건에 넣지 않았다. 완전한 사용자 정의 태그, 속성, CDATA·주석·처리 명령은 기존 동작을 유지한다. 불완전한 태그·속성과 모호한 닫히지 않은 태그는 여전히 거절된다. parser identity는 `financial_parser_v11_literal_angle_boundaries`이며 이전 저장소를 자동 채택하지 않는다.

## 원문 보존 검증

수정 전에 원문 해시와 직접 검토한 문자 위치를 고정 (`../../benchmarks/results/xml_structure_recovery_2026-10-16/frozen_source_edits.json`, local artifact not included)했다. KB 20개, 카카오 4개, 현대자동차 1개의 `<`를 문자 entity로 바꾼 별도 메모리상의 입력을 기존 v10 sanitizer에 통과시켜 대조 기준으로 삼았다. 새 알고리즘으로 기대 결과를 생성하지 않았다. POSCO의 두 표기는 별도의 진단용 대조이며 운영 복구 대상으로 지정하지 않았다.

- 세 파일의 **전체 전처리 문자열과 전체 파싱 트리 직렬화가 고정 기준과 정확히 동일**하다. 기준은 복구를 끈 strict XML 파싱에서도 오류 0이다.
- 수정 없이 통과하던 나머지 **10개 파일의 전체 전처리 문자열·트리 직렬화가 v10과 바이트 단위로 동일**하다. POSCO의 전처리도 동일하며 차단된다.
- **14개 원본 파일 SHA-256이 모두 유지**됐다. 네트워크를 차단한 검증 기록 (`../../benchmarks/results/xml_structure_recovery_2026-10-16/source_verification.json`, local artifact not included)에 결과를 저장했다.
- 실제 `process_document`까지 실행해 KB 2,464개, 카카오 1,460개, 현대자동차 1,266개 청크를 생성했다. 고정한 복구 위치에 연결된 문단에서 얻은 문맥 **27/27개가 청크 본문에 남는다**(공백 정규화 비교). 전달 기록 (`../../benchmarks/results/xml_structure_recovery_2026-10-16/chunk_delivery.json`, local artifact not included). 새 저장소·임베딩은 만들지 않았다.
- [익명 회귀 테스트](../../tests/test_parser_angle_boundaries.py) 7개를 추가했다. 파서·ingest·manifest·import 관련 suite 222개, 후속 entity 누락 회귀 1개, 문서 계약 2개로 **총 225개 통과**했다. 기존 XML 오류 차단과 모호한 태그 거절을 약화하지 않았다. `git diff --check`도 통과했다.

과거 오류를 무시한 트리와 고정 기준의 비교에서 KB는 `<` 89개·`>` 70개·`&` 136개, 카카오는 `<` 40개·`>` 37개·`&` 9개, 현대자동차는 `<` 9개·`>` 9개·`&` 999개가 복원됐다. 이는 처음 손상된 위치뿐 아니라 뒤쪽 정상 entity가 다시 읽힌 결과다. 비어 있지 않은 텍스트 줄 비교에서 기존 문자의 삭제는 없었다. 문자 차이 기록 (`../../benchmarks/results/xml_structure_recovery_2026-10-16/text_loss_summary.json`, local artifact not included). 숫자 자체를 고친 것은 아니며 `1&2 → 12`처럼 누락된 구분자 복원으로 숫자 토큰 경계는 달라질 수 있다.

## POSCO 차단을 유지한 이유

해당 두 표기를 문자로 escape한 진단용 입력은 strict XML 오류가 0이고, 원문 entity 기호 184개와 `<STS>`·`<CG>` 표기를 복원한다. 대조 트리에서 부모 연결 93곳이 달라진다. 그러나 `<NAME>`은 실제 태그와 똑같은 문법이다. 닫는 태그가 없다는 이유만으로 문자로 전환하면 손상된 실제 태그도 정상 문서처럼 수용할 수 있다.

현재 계약에는 이를 구분하는 검토된 DART XSD/태그 분류가 없다. 두 이름을 예외 처리하거나 모든 미닫힘 태그를 문자화하는 규칙은 추가하지 않았다. 이 파일을 운영 파서에서 복구하려면 태그와 본문 표기를 구분할 일반 구조 계약을 먼저 확보해야 한다. 원본이나 저장소를 덮어쓰는 수동 보정도 하지 않았다.

## 범위

검증은 이 문자 경계의 원문 보존과 기존 오류 차단 유지에 한정된다. 파서·청킹 전체의 모든 누락, 표 의미, 숫자 해석, 검색 순위, 모델 답변 정확도를 보증하지 않는다. 기존 v5 앱 저장소와 v9 평가 저장소는 그대로이며 활성화·fresh ingest·모델 호출은 없다. 과거 v10 검증 묶음도 변경하지 않았다.
