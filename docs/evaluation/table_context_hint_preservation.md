# 표 문맥 라벨 오분류 수정과 원문 보존 검증

2026-09-29. [v3 전체 77문항 검색 감사](full77_v3_retrieval_audit.md)에서 발견한
현대자동차 배출권 회계 문단 누락의 후속 수정이다. 제품 파서와 무호출 검증만
수행했으며, 저장소 재구축과 답변 품질 평가는 **NOT_RUN**이다.

## 원인과 수정

`financial_parser._extract_standalone_table_context_hint`는 행·열이 적고 본문
어딘가에 기간·단위·재무제표 이름이 있으면 표 전체를 문맥 라벨로 반환했다.
`block_collection.collect_blocks`는 이를 받은 뒤 본문 블록 생성 전에 건너뛰었다.
한 셀에 긴 회계정책을 넣은 DART 표도 여기에 해당했다. 현대자동차 원문의
11,908자·11,114자 표가 실제로 잘못 분류됐다. TE 셀 인식이나 벡터 검색의 문제가 아니다.

- 전체 텍스트가 기간·날짜·단위·재무제표 제목의 라벨 문법에 맞을 때만 소비한다.
  알 수 없는 문구·본문·작은 숫자 표는 본문 근거로 남긴다.
- 혼합 캡션 표는 본문에 보존하고, 끝에 괄호로 명시된 단위 선언만 다음 표의
  문맥으로 전달한다. 2행·3열 이하에 한하며 명시적인 헤더+데이터 표는 제외한다.
  다음 본문 표가 소비하거나 문단 경계를 만나면 기존 수명 규칙대로 종료한다.
- 본문에 있는 비율, 금액, ‘단위원가’를 다음 표의 단위로 승격하지 않는다.
  원문 단위 선언을 그대로 전달하며 의미상 올바른 단위인지 새로 추론하지 않는다.
- 회사·문항·정답별 분기나 검색·답변 프롬프트 변경은 없다. 단위 추론기 자체를
  재설계하지 않았으며, 모르는 캡션을 새 소제목으로 추정하지 않는다.

Owner는 `src/processing/financial_parser.py`, `src/processing/block_collection.py`다.
`src/config/runtime_contract.py`의 파서 식별자를
`financial_parser_v4_label_only_table_context`로 갱신했다.

## 검증 결과

네트워크를 차단하고 기존 11개 보고서의 473개 절을 수정 전후로 파싱했다.
전후 모두 절별 시간 제한 0을 명시했고 timeout fallback은 없었다.
원본 SHA를 확인했으며, 이전 동작은 이번 작업 시작 시 보존한 함수로 재현했다.

| 항목 | 결과 |
| --- | --- |
| 원문 절 목록 | 전후 동일, 473개 |
| 기존 블록 텍스트·유형·소제목 | 19,408개 모두 보존, 중복 개수 포함 |
| 기존 대응 표의 grid | 동일 |
| 블록 수 | 19,408 → 20,967, 1,559개 추가 |
| 현대자동차 회계정책 2개 | 각각 6개·5개 청크로 보존 |
| LG에너지솔루션 같은 배출권 문구 포함 표 2개 | 각각 1개·3개 청크로 보존 |
| 위 네 표의 전체 원문 | 공백만 제외한 순서·내용이 청크 연결에 그대로 존재 |
| 기존 블록의 unit_hint | 26개 변경, 이전 문맥 출처를 별도 검토 |
| 추가 회귀 테스트 | 10개 통과; 이전 동작은 7개 메서드에서 실패 |
| 최종 전체 테스트 | 2,154개 통과, 88.605초 |
| 보호 파일 | 188개 동일, 기존 저장소 파일 목록·바이트와 .env 보존 |
| provider/임베딩 호출·API 비용 | 0회·USD0 |

추가 1,559개는 본문·주석·혼합 캡션을 모두 포함한 **블록 수**다. 독립 문항 수나
복구한 정답 수가 아니다. 전체 표 메타데이터 동일성, 모든 원문의 완전 추출,
모든 숫자의 단위 의미 정확성을 주장하지 않는다. 추가 블록 때문에 표 순번·청크 ID,
기간/헤더 문맥, 입력 크기와 검색 순위도 달라질 수 있다.

26개 변경은 이전 본문의 비율·금액·‘단위원가’ 등을 다음 표의 단위로 넘기던
문맥 제거와 연결된다. 실제 이전 `context_prefix`를 다시 수집해 대조했으며,
이 26개에는 끝에 명시된 단위 선언이 없었다. 바뀐 `unit_hint`를 모두 올바른
단위로 의미 평가했다는 뜻은 아니다. 본문 뒤에 공백 없이 붙은 명시 단위는
별도 회귀 테스트로 보존을 확인했다.

초기 라벨 제한안에서는 혼합 캡션의 단위 전달도 끊겼다. 같은 처리 경계에
명시 단위 suffix 전달을 추가해 보완하고 11개 보고서 비교와 전체 테스트를 다시
실행했다. 초기 결과와 실패 로그는 보존했다. 테스트의 기존 라벨 줄바꿈 기대값과
schema 버전 기대값도 실제 기존 계약에 맞췄다. 최종 이전 동작 재현은 수정된
동일 테스트를 사용하며 23개 subtest 실패를 23개 독립 테스트로 세지 않는다.

## 저장소 반영 범위와 산출물

현재 `.env`가 가리키는 `data/app_full11_2023_20260929`와
`dart_reports_v3_full11_2023`은 **v3 그대로**다. 실제 manifest 검사는 v4 코드와의
`mismatch`, `ready=false`를 반환한다. 기존 파일을 자동 수정하거나 호환성 검사를
완화하지 않았다. 현재 코드로 앱을 다시 시작하면 기존 v3 저장소는 준비 상태가 아니다.

실제 검색 반영에는 같은 11개 원문을 v4로 재파싱해 **별도 저장소**를 만들고,
저장 후 원문 조회·검색·준비 상태를 검증해야 한다. 한 청크 교체나 manifest 문자열만
바꾸는 방식은 사용할 수 없다. 정확히 같은 임베딩 입력의 기존 벡터 재사용 가능성과
새 입력 비용 산정은 다음 재구축 준비에서 확인한다. 이번 작업은 그 구축을 실행하지 않았다.

`benchmarks/results/standalone_table_hint_fix_2026-09-29/`에 수정 전 source 사본,
원본 표 조사, 이전 동작 replay, 테스트 로그와 보호 hash를 저장했다.
`verified/`에는 최종 보고서별 블록 비교, 추가 본문/표 구조, 단위 변경과 이전 문맥,
네 표의 청크 직렬화/읽기 검증, 전체 테스트 및 실제 v3/v4 readiness 결과가 있다.
`final/`이라는 초기 중간 산출물 폴더도 덮어쓰지 않고 보존했다.
이전 strict 11/12 답변 결과와 77문항 v3 검색 결과도 그대로이며 새 성능 수치가 아니다.
