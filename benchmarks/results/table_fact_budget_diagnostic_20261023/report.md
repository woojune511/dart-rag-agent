# 문맥 예산 확대의 저장 결과 진단

**예산을 늘리면 Motional의 두 목표 값이 실제로 전달된다. 64KiB 고정 실험만으로 표현 방식의 가능성을 부정할 수 없다.**

64KiB는 현재 앱의 코드상 기본 제한(`src/config/simple_rag.py:6`)이다. 이번에는 앱 설정을 고치지 않고 저장된 FCT12 값 단위와 기존 순서를 그대로 사용해 예산만 메모리에서 바꿨다. 64KiB 재계산은 이전 packet hash와 모든 예산 결정에 정확히 일치했다.

| 문맥 상한 | 실제 bytes | Motional 지분율 25.81 | 장부금액 1,294,367 |
|---:|---:|---|---|
| 64 KiB | 65,443 | 미전달 | 미전달 |
| 72 KiB | 73,727 | 미전달 | 미전달 |
| 80 KiB | 81,913 | 미전달 | 미전달 |
| 96 KiB | 98,233 | 미전달 | 미전달 |
| 128 KiB | 131,066 | 미전달 | 미전달 |
| 160 KiB | 163,836 | 전달 | 전달 |
| 192 KiB | 196,556 | 전달 | 전달 |

검사한 7개 상한 중 160KiB와 192KiB에서 두 값이 모두 전달됐다. 160KiB는 원래 상한의 2.5배다. 정확한 최소 예산을 찾은 것은 아니며, 임의의 중간 상한에서 같은 결과가 난다고 단정하지 않는다.

이전 64KiB 로그의 제안 크기 65,610·65,614바이트만 보고 74~78바이트를 더하면 된다고 볼 수는 없다. 예산이 커지면 먼저 제외됐던 앞쪽 값들이 다시 들어가므로, 전체를 같은 순서로 재계산해야 한다. 128KiB에서도 앞부분 값 1,294개가 먼저 들어가 목표 행은 빠졌고, 160KiB에서는 1,701개가 들어가며 목표 행까지 도달했다.

앞선 판단을 좁힌다. 확인된 사실은 “64KiB의 원문 순서 첨부에서는 목표 값이 빠짐”이었다. 예산 확대로 전달 누락이 해소된 현재, 이 형식을 폐기하거나 더 복잡한 선택기를 우선해야 한다는 결론은 뒷받침되지 않는다. 예산 확대 조건의 전체 근거 보존과 생성 답변을 확인하기 전까지 제품 채택 판단은 보류한다.

이 진단은 Motional 한 문항의 지분율·장부금액 전달만 확인했다. 77문항 회귀, 전체 요약손익의 충족, 서술형 표 보강 손실, 생성 답변 정확도·출처 충실도·토큰 비용은 재평가하지 않았다. byte 상한 비율을 token 수나 API 비용 비율로 해석하지 않는다. 개발 중 이미 본 실패 사례를 대상으로 한 사후 진단이다.

실행 144.18초, 외부 API 호출 0회·$0, 원문 projector 재실행 0회, 답변 생성 0회. 기존 구현·.env·v12 store와 이전 실험 산출물을 포함한 보호 파일 218개가 그대로이며 Git HEAD/index/작업 상태도 동일하다. 앱 재시작이나 커밋은 하지 않았다.

ARS 검증 범위: 결정론적 단일 사례의 예산 민감도. 통계적 유의성·일반화 주장을 하지 않으며 11개 오류 유형 검토는 validation.json에 기록했다. 결과와 재현 범위는 results.json, contract.json, preservation.json을 따른다.
